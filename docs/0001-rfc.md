# RFC 0001 — `school_menu` Home Assistant integration

Status: **Draft, awaiting decisions** · Author: Juergen + Claude · Date: 2026-09-25

## 1. Problem

The school (Waldorf Charlottenburg, catered by Organiced Kitchen) emails one PDF per week
listing Monday–Friday, three lines per day. Today that information lives only in a mailbox.
We want today's and tomorrow's lunch visible in Home Assistant, on a dashboard, without
manual steps.

### Goals
- Today's and tomorrow's menu as sensors, correct at every hour of every day including weekends.
- Survive restarts; several weeks coexist; re-importing a week overwrites it.
- Never break the recorder or throw on a day with no data.
- UI-only setup (config flow), HACS-installable, unit-tested parser.

### Non-goals
- Allergen *interpretation* or dietary filtering (we expose codes, we do not judge them).
- Translating dish names. German text is passed through verbatim.
- Multiple schools in one config entry, historical analytics, shopping lists.
- OCR. The source PDFs carry a real text layer (verified).

## 2. What the real PDFs actually look like

Both samples (`AHS Speiseplan 26-39.pdf`, `26-40.pdf`) are single-page A3, generated by
MS Word, with a clean text layer. Structure, verified on both:

```
WOCHENPLAN
21.09.26 – 25.09.26          <- DD.MM.YY, EN DASH (U+2013)
MONTAG                        <- uppercase day anchor
Pasta mit Käsesauce / Frische Kräuter (1a, 3)
Blattsalat mit gerösteten Kernen (4)
Obst
... DIENSTAG / MITTWOCH / DONNERSTAG / FREITAG, 3 lines each ...
„<quote>“ / <author> / (Änderung Vorbehalten) / allergen legend / contact footer
```

Three findings that change the spec:

**F1 — "main / side / dessert" is not semantically reliable.** On Wednesday in *both*
weeks the third line is a salad, not a dessert (`Soja geschnetzeltes / Reis / Blattsalat`).
The three lines are typographically identical — there is no font or size signal to recover
roles from. Position is all we have. Recommendation: keep the three field names as a
*positional* contract, document them as such, and additionally expose a `lines` array so
the card and any automation can treat them as "three lines" when that is more honest.

**F2 — Allergen codes are trailing parentheticals** (`(1a, 3)`, `(4)`) and separate cleanly
with one regex. Recommendation: strip them from the dish text into a per-line `allergens`
list, and keep a `*_raw` variant with them intact. `sensor.school_menu_today` state should
be the *clean* main course, because the raw form eats the 255-char state limit for no benefit.

**F3 — The date range is always present in the header**, so the "fall back to a user-selected
week" branch in the brief is a genuine edge case, not the norm. Filenames also encode
`YY-KW` (`26-40`), giving a cheap cross-check. All five dates are derived as
`monday + timedelta(days=0..4)`, which is year-boundary safe (a week spanning New Year
derives correctly from the start date alone).

## 3. Key decisions

### D1 — PDF library: **pypdf** (reversing my initial assumption)

I assumed pdfplumber, then measured. On both real files:

| | output | speed | install |
|---|---|---|---|
| pypdf 6.19 | *byte-identical line sequence* | ~11 ms | **4 MB, 1 package** |
| pdfplumber 0.11 | *byte-identical line sequence* | ~26 ms | 48 MB, 8 packages (pdfminer.six, pillow, cryptography, pypdfium2, cffi…) |

pdfplumber's value is word-level x/y geometry and table extraction. This layout is centered
running text with no table and correct reading order, so that capability buys nothing today.
12× the install weight and a compiled-wheel dependency chain (cryptography, pillow) on an
LXC is a real cost for a hobby integration. **Recommend pypdf**, pinned in `manifest.json`.
If the caterer ever moves to a column/table layout, swapping the extraction function inside
the isolated parser module is a contained change — that is exactly why the parser has no HA imports.

### D2 — Storage: **`homeassistant.helpers.storage.Store`**

Alternatives: keep in `hass.data` (lost on restart — fails the requirement); `RestoreEntity`
(designed for a single state, not a multi-week corpus); a JSON file we manage ourselves
(reimplements `Store`, loses atomic writes and the migration hook). `Store` with an explicit
`version`/`minor_version` and an `async_migrate_func` is the standard answer and gives us
debounced atomic writes for free. One store per config entry, pruned to the last **4** weeks on write.

### D3 — Email ingestion: **built-in IMAP polling inside the integration** (option b)

Given your answer that the mail lands in a plain IMAP mailbox with nothing consuming it:

- **(a) Core IMAP integration + automation.** Attractive because it is zero new code, but the
  core integration is built around firing `imap_content` events with message *text*; getting a
  binary attachment onto disk from an automation is the weak link and typically ends in a
  `shell_command` hack. Fragile for the one step that matters most.
- **(b) Built-in polling.** We own an `aioimaplib` client (same library core uses), poll every
  15 min, filter by sender + subject, SHA-256 the attachment for dedup, credentials live in
  `entry.data` and are redacted in diagnostics. Self-contained, testable, and the acceptance
  criterion ("new email updates sensors within 15 min, no manual steps") falls out directly.
  Cost: we maintain IMAP code and must handle auth failures as `ConfigEntryAuthFailed` → reauth flow.
- **(c) Paperless-ngx.** You run it, but it is not currently consuming this mailbox, so this is
  not the "free" option it would be otherwise. It adds a second system in the critical path and
  moves half the configuration (mail rules, tags) outside HA. Genuinely good if you later want
  the PDFs *archived*; overkill as a transport.

**Recommend (b)**, with the mail client in its own module so it can be tested against a fake
IMAP server. If you later route the mailbox into Paperless anyway, (c) becomes a second,
additive source rather than a rewrite.

### D4 — Card: **Mushroom template card as the primary, custom Lit card as the optional extra**

You already run Mushroom. A `mushroom-template-card` (or a stacked pair for today/tomorrow)
gets theme variables, light/dark and mobile width for free, needs no build toolchain, no
`/local` resource registration, and cannot break on a frontend upgrade the way a hand-rolled
card can. A custom Lit card's real advantages are a visual editor and precise control of the
empty state — nice, but it means shipping a Rollup/TS build, a versioned `dist/`, and a second
HACS resource for a card that renders five strings. **Recommend the Mushroom YAML variant as
the documented default**; I will still deliver the Lit card in M3 as you asked, clearly marked optional.

### D5 — Custom integration vs. Mealie: **custom integration**

Mealie is recipe- and meal-plan-centric. Mapping "Obst" or "Blattsalat mit gerösteten Kernen"
onto Mealie recipes creates junk entities, and we would still need a PDF parser plus a second
sync hop. Mealie earns its place when you want recipes, nutrition and shopping lists. Rejected.

## 4. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Caterer changes the PDF layout | Strict validation (5 days × 3 non-empty lines). On failure: **keep previous data**, raise a persistent notification naming the reason and the file. Parser is HA-free and fixture-tested, so a fix is a unit-test loop, not an HA restart loop. |
| A dish name wraps to a second line, yielding 4 lines for a day | Currently never happens (verified, A3 is wide). Would trip validation rather than silently mis-assign. See open question Q3. |
| Positional roles wrong (F1) | Document the contract; expose `lines` alongside the named fields. |
| A day genuinely missing / holiday week | Per your Phase 0 answer: absence of data only. State `none`, `reason: no_menu`. No holiday calendar. |
| HA API drift after my May 2026 cutoff | Config-flow and entity APIs I will verify against current developer docs before Phase 3 rather than from recall; I will call out anything I cannot confirm. Flagging now: exact `ConfigFlow`/`OptionsFlow` signatures and `async_forward_entry_setups` details are the likeliest drift points. |
| IMAP credentials | `entry.data` only, never logged, never in attributes, redacted in `diagnostics.py`, reauth flow on `ConfigEntryAuthFailed`. |
| `file_path` service abused to read arbitrary files | Resolve symlinks and `..`, then require the real path to sit under `/config/www` or `/media`; reject otherwise. |

## 5. Decisions requested

1. **D1 — pypdf instead of pdfplumber?** (evidence above; this reverses my Phase 0 assumption)
2. **D3 — built-in IMAP polling** as the M2 path?
3. **D4 — Mushroom template card** as the documented default, Lit card shipped as optional?
4. **F1/field naming** — keep `main` / `side` / `dessert` as positional names *plus* a `lines`
   array, or rename to something role-neutral?
5. **F2/allergens** — strip codes out of the dish text into an `allergens` attribute
   (my recommendation), or keep them inline in the sensor state?
6. **Q3 — strictness:** if one day has ≠ 3 lines, reject the whole PDF and keep previous data
   (strict, my recommendation), or import the days that are well-formed and flag the rest?
7. **HACS packaging** — GitHub owner/repo slug, and do you want the CI scaffolding
   (hassfest + HACS validation workflows, issue templates) generated too?
